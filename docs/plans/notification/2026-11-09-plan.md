# 1. Context

**Problem:**  
Nền tảng Ordera Multi-Tenant Loyalty & Ordering cần phân hệ backend hoàn chỉnh cho Hộp thư thông báo ("Content for you" - Figma 05.01, 05.02, 05.03) và tiếp nhận phiếu khiếu nại thiếu điểm tích lũy cũ.
Hệ thống cần cung cấp 6 API endpoints chuẩn RESTful, đảm bảo:
- Phân lập đa thương hiệu (Multi-Tenant Isolation qua `TenantContextHolder`).
- Cơ chế Fan-out on Read: Thông báo chung lưu tại `system_notifications`, trạng thái đọc lưu tại `user_notifications`.
- Tiếp nhận phiếu khiếu nại, sinh mã đối soát `INQ-YYYYMMDD-XXX`, lưu tại `support_inquiries`.
- Clean Architecture 4 lớp: Domain -> Application -> Infrastructure -> Presentation.

**Affected Modules:**  
- `com.ordera.modules.notification` — Module Clean Architecture mới hoàn chỉnh.
- `com.ordera.config.SecurityConfig` — Bổ sung đường dẫn `/api/v1/notifications/**` và `/api/v1/support/**` vào whitelist permitAll() để xử lý xác thực linh hoạt trong Use Case / Controller.

**Non-Goals:**  
- Gửi push notification FCM/APNS (được xử lý ở phase sau qua Message Broker).
- Upload file vật lý trực tiếp lên AWS S3 (ở phase hiện tại, API nhận đường dẫn `receiptPhotoUrl` sau khi client upload lên CDN hoặc validate metadata file).

# 2. Constraints

**Tech Stack:**  
- Java 21 LTS, Spring Boot 3.3.5
- Spring Data JPA, PostgreSQL 16
- MapStruct, Lombok, Jakarta Validation
- Spring Security 6

**Architecture Rules:**  
- **Clean Architecture 4 Lớp:** Domain không phụ thuộc tầng ngoài; Application phụ thuộc Domain; Infrastructure và Presentation phụ thuộc Application & Domain.
- **Multi-Tenant Isolation (Bắt buộc):** Mọi truy vấn database nghiệp vụ đều phải lọc theo `tenant_id` qua `TenantContextHolder`.
- **Chống God Method (Orchestrator Pattern):** Hàm `execute()` trong UseCase chỉ điều phối các bước tối đa 30–40 dòng; tách nhỏ thành private helper methods (`validateInquiryInput()`, `generateTicketCode()`, `saveInquiryRecord()`, `updateReadStatus()`).
- **Null-Safety & Guard Clauses:** Kiểm tra null an toàn, early return, nesting depth <= 3.
- **Không Magic Numbers / Magic Strings:** Toàn bộ hằng số gom về `NotificationConstants` và `NotificationMessages`.
- **Mã lỗi chuẩn hóa:** `NotificationErrorCode` implement `ErrorCode`, ném qua `BusinessException`. Cấm tạo exception classes riêng lẻ.
- **Chuẩn phản hồi:** `ApiResponse.ok(NotificationMessages.MSG_*, data)` hoặc `ApiResponse.created(NotificationMessages.MSG_*, data)`. Không hardcode string trong `ApiResponse`.

# 9. Edge Cases & Handling

| Tình huống biên (Edge Case) | Cách xử lý | Handled In |
|---|---|---|
| User chưa đăng nhập gọi API 8.1 - 8.5 | Ném `BusinessException(UNAUTHORIZED)` | Task 5 |
| User chưa đăng nhập gọi API 8.6 (gửi hỗ trợ) | Cho phép, `userId = null`, đối soát qua Email và SĐT | Task 5 |
| Header `X-Tenant-ID` bị thiếu hoặc null | Interceptor / UseCase ném `TENANT_HEADER_MISSING` | Task 5 |
| File chứng từ đính kèm vượt quá 5MB | Validate dung lượng `MAX_RECEIPT_IMAGE_SIZE_BYTES` | Task 5 |
| Đánh dấu tin đã đọc khi bản ghi `user_notifications` chưa tồn tại | Tạo mới bản ghi với `is_read = true`, `read_at = now()` | Task 5 |
| Đánh dấu đã đọc khi bản ghi đã tồn tại với `is_read = true` | Cập nhật idempotency an toàn, không báo lỗi | Task 5 |
| Đánh dấu tất cả đã đọc khi hộp thư rỗng | Trả về `markedCount = 0`, `unreadCount = 0` | Task 5 |
| Trùng mã `ticket_code` trong cùng 1 ngày | Số thứ tự sequence `XXX` đếm từ các ticket đã tồn tại trong ngày + 1 | Task 5 |
