# 1. Context

**Problem:**  
Ordera là nền tảng quản trị khách hàng thân thiết và đặt món đa thương hiệu (Multi-Tenant Loyalty & Ordering Platform). Hiện tại, hệ thống đã có migration CSDL `V2__create_users_and_identity.sql` và `V3__create_loyalty_and_tiers.sql`, nhưng chưa có phân hệ xác thực hoàn chỉnh để khách hàng đăng nhập không mật khẩu (qua SMS OTP), đăng ký tài khoản hội viên 2 bước (SMS/Email OTP), cấp phát và xoay vòng JWT (HMAC-SHA512), cũng như kiểm soát chống spam cooldown 120s, khóa phiên sau 5 lần nhập sai và thu hồi token qua Redis Blacklist theo kiến trúc Clean Architecture 4 lớp.

**Affected Modules:**  
- `com.ordera.modules.auth` — Toàn bộ 4 lớp: Domain (Pure POJOs, `AuthErrorCode`), Application (5 Use Cases theo Orchestrator Pattern, Outbound Ports), Infrastructure (JPA Entities, Repositories, Adapters Telnyx/MailHog/Redis, MapStruct DTO Mapper), Presentation (`AuthController` bọc `ApiResponse<T>`).
- `com.ordera.common.util` — Bổ sung `OtpUtils` (sinh OTP 6 số, SHA-256 hash, mask số điện thoại / email).
- `com.ordera.modules.loyalty` — Tái sử dụng `MemberProfileRepository` và `TierDefinitionRepository` để tự động khởi tạo hồ sơ hội viên New Member (0 điểm) khi đăng ký thành công.
- `com.ordera.config` — Đảm bảo `SecurityConfig` cho phép các endpoint `/api/v1/auth/**` truy cập công khai không yêu cầu token trước đó (ngoại trừ `/api/v1/auth/logout` có thể đọc token từ header `Authorization`).

**Non-Goals:**  
- Không thay đổi các bảng CSDL đã định nghĩa trong Flyway V2 và V3.
- Không triển khai các tính năng đặt món, giỏ hàng hay thanh toán trong phân hệ này.
- Không tích hợp SMS gateway thật (dùng mock log adapter trong môi trường dev).

# 2. Constraints

**Language & Framework:** Java 21 LTS, Spring Boot 3.3.5, Spring Security 6, Spring Data JPA, Spring Data Redis, Flyway, MapStruct, Lombok, JJWT 0.12.6.  
**Architecture:** Clean Architecture 4 lớp (Presentation ➜ Application ➜ Domain ➜ Infrastructure).  

**Rules:**  
- **Tầng Domain độc lập tuyệt đối:** Không chứa bất kỳ import nào từ `org.springframework.*` hay `jakarta.persistence.*`.
- **Quản lý ngoại lệ tập trung:** Sử dụng `AuthErrorCode` (implement `ErrorCode`), ném lỗi qua `BusinessException`. Cấm tạo các class Exception riêng lẻ.
- **Orchestrator Pattern:** Các phương thức `execute()` trong UseCaseImpl chỉ đóng vai trò điều phối luồng, phân rã logic chi tiết thành các private helper methods có tên tường minh.
- **Multi-Tenant Isolation:** 100% các truy vấn DB và Redis Keys đều phải lọc và gắn tiền tố theo `tenantId` (`TenantContext.getTenantId()`).
- **Phản hồi chuẩn RFC 7807:** Mọi phản hồi thành công bọc trong `ApiResponse<T>`, phản hồi lỗi trả về format RFC 7807 chuẩn qua `GlobalExceptionHandler`.

# 3. Conventions

**Naming:**  
- Domain Models: `User`, `UserRole`, `UserStatus`, `OtpSession`, `TokenPair`, `OtpChannel`, `OtpPurpose`.
- Error Codes: `AuthErrorCode` (`OTP_INVALID`, `OTP_EXPIRED`, `OTP_COOLDOWN_ACTIVE`, `OTP_MAX_ATTEMPTS_EXCEEDED`, `PHONE_ALREADY_EXISTS`, `INVALID_CREDENTIALS`, `TOKEN_EXPIRED`, `TOKEN_REVOKED`, etc.).
- Outbound Ports: `SmsSenderPort`, `EmailSenderPort`, `OtpStoragePort`, `TokenBlacklistPort`.
- Use Cases: `<Action>UseCase` interface và `<Action>UseCaseImpl` class.
- Adapters: `TelnyxSmsAdapter`, `MailHogEmailAdapter`, `RedisOtpStorageAdapter`, `RedisTokenBlacklistAdapter`.
- Service: `JwtTokenProviderService`.
- Controllers: `AuthController`.
- Unit Tests: `should_<expected>_when_<condition>()`.

**Error Handling:**  
- Ném lỗi bằng `throw new BusinessException(AuthErrorCode.<ERROR_CODE>)` hoặc `throw new BusinessException(AuthErrorCode.<ERROR_CODE>, customMessage, details)`.

**Logging:**  
- Sử dụng `@Slf4j` từ Lombok. Ghi log có cấu trúc tại entry point của UseCase và các thời điểm quan trọng (gửi OTP, xác thực thành công, đưa token vào blacklist). Không log mã OTP dạng plain text ở production log level.

# 4. Contracts

## 4.1 Interface: `SendOtpUseCase`
```java
SendOtpResponse execute(SendOtpRequest request);
// pre: TenantContext.getTenantId() != null; request.phoneNumber() valid E.164; request.channel() != null
// post: Sinh OTP 6 số, kiểm tra cooldown (120s), lưu Redis TTL 120s, gửi SMS qua SmsSenderPort, ghi OtpAuditLog
// throws: BusinessException(TENANT_HEADER_MISSING) nếu tenantId null
//         BusinessException(OTP_COOLDOWN_ACTIVE) nếu đang trong thời gian 120s cooldown
```

## 4.2 Interface: `VerifyOtpUseCase`
```java
VerifyOtpResponse execute(VerifyOtpRequest request);
// pre: TenantContext.getTenantId() != null; request.phoneNumber() valid E.164; request.otpCode() matches ^\d{6}$
// post: Kiểm tra attempt count (< 5). Nếu khớp OTP: đánh dấu verified, cấp TokenPair JWT nếu user đã tồn tại (isProfileComplete = true); nếu user chưa tồn tại trả isProfileComplete = false.
// throws: BusinessException(OTP_MAX_ATTEMPTS_EXCEEDED) nếu attempts >= 5
//         BusinessException(OTP_EXPIRED) nếu không tìm thấy OTP trong Redis
//         BusinessException(OTP_INVALID) nếu mã không khớp (tăng attempt count)
```

## 4.3 Interface: `SendRegisterOtpUseCase`
```java
SendRegisterOtpResponse execute(SendRegisterOtpRequest request);
// pre: TenantContext.getTenantId() != null; request != null
// post: Kiểm tra phone/email chưa đăng ký. Kiểm tra cooldown. Sinh OTP, lưu Redis, gửi qua SMS hoặc Email Port, ghi audit log
// throws: BusinessException(USER_ALREADY_EXISTS) nếu SĐT hoặc Email đã tồn tại trong tenant
//         BusinessException(OTP_COOLDOWN_ACTIVE) nếu đang trong cooldown
```

## 4.4 Interface: `VerifyRegisterOtpUseCase`
```java
VerifyRegisterOtpResponse execute(VerifyRegisterOtpRequest request);
// pre: TenantContext.getTenantId() != null; request != null
// post: Đối soát OTP. Tạo UserJpaEntity + MemberProfileJpaEntity (Tier New, 0 pts, barcode) trong 1 Transaction. Cấp phát TokenPair JWT.
// throws: BusinessException(OTP_INVALID) hoặc BusinessException(OTP_EXPIRED)
//         BusinessException(USER_ALREADY_EXISTS) nếu race condition đã đăng ký
```

## 4.5 Interface: `RefreshTokenUseCase`
```java
RefreshTokenResponse execute(RefreshTokenRequest request);
// pre: TenantContext.getTenantId() != null; request.refreshToken() non-blank
// post: Kiểm tra chữ ký JWT, kiểm tra claim type == 'refresh', kiểm tra blacklist. Cấp phát cặp AccessToken và RefreshToken mới (xoay vòng token).
// throws: BusinessException(REFRESH_TOKEN_EXPIRED) nếu token hết hạn
//         BusinessException(TOKEN_REVOKED) nếu nằm trong blacklist
```

## 4.6 Interface: `LogoutUseCase`
```java
void execute(String authHeader, LogoutRequest request);
// pre: authHeader starts with "Bearer " (hoặc request có refreshToken)
// post: Trích xuất jti và thời gian sống còn lại của Access Token, lưu vào Redis Blacklist (auth:blacklist:{jti}) với TTL tương ứng.
```

# 9. Edge Cases

| Tình huống ngoại lệ | Hành vi mong đợi | Handled In |
|:---|:---|:---:|
| Spam gửi lại OTP liên tục | Trả về HTTP 429 `OTP_COOLDOWN_ACTIVE` kèm thời gian chờ còn lại | Task 8 |
| Nhập sai OTP lần 1–4 | Trả về HTTP 400 `OTP_INVALID` kèm số lần thử còn lại (`remainingAttempts`) | Task 9 |
| Nhập sai OTP lần thứ 5 | Hủy OTP, khóa phiên 15 phút, trả về HTTP 429 `OTP_MAX_ATTEMPTS_EXCEEDED` | Task 9 |
| OTP quá 120 giây | Trả về HTTP 400 `OTP_EXPIRED` | Task 9, 10 |
| Đăng ký với SĐT đã có tài khoản | Trả về HTTP 409 `PHONE_ALREADY_EXISTS` / `USER_ALREADY_EXISTS` | Task 8, 10 |
| Sử dụng Refresh Token đã bị thu hồi | Trả về HTTP 401 `TOKEN_REVOKED` | Task 11 |
| Header `X-Tenant-ID` bị thiếu | Trả về HTTP 400 `TENANT_HEADER_MISSING` | Task 8, 9, 10, 11, 12 |
| Gọi Logout không có Authorization header | Bỏ qua nếu có refreshToken trong body, hoặc trả về thành công idempotency | Task 11, 12 |

# 10. Risks & Mitigations

| Rủi ro | Mức độ | Biện pháp giảm thiểu |
